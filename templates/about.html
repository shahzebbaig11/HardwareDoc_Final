About This Project

Expert System for Computer Hardware Fault Diagnosis Using Backward Chaining, with WHY and HOW Explanation Facilities

What Problem Does This Solve?

When a computer stops working, diagnosing the cause requires methodical reasoning. A user without technical knowledge may not know which component to check first, which symptoms are significant, or which questions to ask themselves.

This application is a rule-based expert system that captures the reasoning process of a hardware technician in the form of structured IF-THEN rules. It interviews the user with only relevant questions, reasons through those rules, and produces a traceable, explainable diagnosis — without requiring any technical expertise from the user.

It is a BCA Mini-Project demonstrating the practical implementation of backward-chaining inference — a fundamental concept in Artificial Intelligence and Knowledge-Based Systems.

How Backward Chaining Works

Backward chaining is a goal-driven inference strategy. Instead of applying all known facts to derive every possible conclusion (forward chaining), the engine starts from a hypothesis — a specific fault — and works backward to find facts that would prove it.

  1. Select a goal (a specific fault to investigate, e.g. "no power").
  2. Find all IF-THEN rules whose THEN part matches the goal.
  3. For each rule, try to prove all IF premises.
  4. If a premise is already in working memory (a previous answer), use it directly.
  5. If a premise is unknown, check if another rule can prove it (recursive step).
  6. If no rule can prove it, ask the user a question.
  7. If all premises of a rule are proved, the goal is established.
  8. If a premise is disproved, try the next alternative rule (backtracking).
  9. If no rule succeeds, the system reports insufficient evidence.

This approach means the system only asks questions relevant to the current hypothesis, and stops the moment a conclusion is proved or all possibilities are exhausted.

A Concrete Example

Suppose the user selects the goal "No Power". The engine has this rule:

Rule R01 IF no_power_sign AND power_cable_disconnected
THEN fault_power_cable_disconnected (confirmed)
↓ engine tries to prove both premises
Premise 1 no_power_sign — asks: "Does the computer show any sign of power?"
User answers: No → no_power_sign = TRUE
↓
Premise 2 power_cable_disconnected — asks: "Is the main power cable disconnected?"
User answers: Yes → power_cable_disconnected = TRUE
↓ both premises proved
Conclusion fault_power_cable_disconnected — CONFIRMED ✓

If the user had answered "No" to the cable question, the engine would backtrack, try the next rule (e.g. faulty PSU), and ask further questions only relevant to that rule.

WHY Explanation Facility

During diagnosis, every question has a "Why is this being asked?" button. Clicking it reveals:

  • Which diagnostic goal is currently under investigation.
  • Which rule requires this fact as a premise, and what it would prove.
  • The question's own explanation — why this symptom matters clinically.
  • Which facts have already been established in this session.

The WHY explanation is generated in real time from the live inference state — it is not pre-written. Different answers to earlier questions lead to different WHY responses for later questions.

Example: "Is the PSU fan spinning?" is asked because the engine is currently trying to prove Rule R03 (PSU suspected fault), which requires the fact psu_fan_not_spinning as one of its premises.

HOW Explanation Facility

After a diagnosis is complete, the "How was this concluded?" link shows the complete reasoning trace:

  • The diagnostic goal and the final conclusion.
  • A numbered sequence of every inference step taken.
  • Which rules fired (all premises proved) and which failed (and why).
  • Each premise's fact ID, the question asked, and the answer recorded.
  • Which rules were skipped because an earlier premise was already disproved.

The HOW explanation never invents rule firings. Only steps that actually happened during the engine's execution are shown. If a rule failed, it is listed as "not applicable" with the reason.

How Answers Affect Reasoning

  • Yes — sets the corresponding fact to TRUE in working memory. Any rule that requires this fact as a positive premise can now fire (if other premises are also met).
  • No — sets the fact to FALSE. Rules that require it as a positive premise are immediately eliminated. The engine backtracks and tries the next alternative rule.
  • Unknown — records the fact as UNKNOWN. The engine does not treat unknown as No. It may still ask further questions to try alternative rules that do not require this fact. If no conclusion can be reached, it reports insufficient evidence rather than guessing.

System Limitations

  • The system only covers faults explicitly encoded in its {{ rules | length }} rules. Unknown faults are reported as "insufficient evidence".
  • Diagnosis is based on observable symptoms described by the user — hardware that requires physical testing (e.g., multimeter readings) cannot be fully diagnosed here.
  • The system assumes the user's observations are accurate. Incorrect answers lead to incorrect diagnoses.
  • It is designed for educational use only. It is not a substitute for a qualified hardware technician.
  • Never open or attempt to repair a power supply unit — it contains dangerous voltages even when unplugged.

⚠ Safety & Disclaimer

This application is designed for educational use only. All diagnoses produced are based on rule-based reasoning from limited observable symptoms and are not a substitute for professional hardware testing or repair.

  • Always consult a qualified computer technician for hardware repairs.
  • Never open or attempt to repair a power supply unit — it contains dangerous voltages.
  • Do not touch exposed components inside a computer while it is powered on.
  • Handle RAM, CPUs, and other components with proper anti-static precautions.
